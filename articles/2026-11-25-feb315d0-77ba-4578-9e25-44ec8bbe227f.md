## 问题场景

短链调用异常被统一捕获后重新抛出自定义异常，日志里只剩“操作失败”，原始堆栈丢失。

## 实现步骤

捕获底层异常后用 raise ... from e 重新抛出，保留 __cause__。

```python
class CallError(RuntimeError):
    def __init__(self, ident, cause):
        super().__init__("短链调用失败: %s" % ident)
        self.ident = ident
        self.cause_type = type(cause).__name__
```

自定义异常携带业务标识，日志同时打印 cause 的类型与消息。

```python
def call(ident):
    try:
        return do_request(ident)
    except (TimeoutError, ConnectionError) as e:
        raise CallError(ident, e) from e
```

对可恢复的错误单独分支，不把重试和致命错误混在同一层处理。

```python
try:
    call("link-1")
except CallError as e:
    print(e, "|", e.cause_type, "|", type(e.__cause__).__name__)
```

## 验证方法

触发一次底层异常，检查打印的堆栈里是否同时出现自定义异常与原始异常。

## 注意事项

raise ... from None 会主动切断因果链，只有确定底层异常会误导时才用；异常包装不要丢失原错误码。

针对这类偶发问题，尽量把决策依据写进变更说明，避免资源被长期占用。

对于刚接手的同学，要明确各项资源的释放时机，确认指标平稳后再逐步放开。

在资源受限的环境下，要避免在高峰期执行这类操作，避免问题积累到难以收场。

在实际落地时，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。

经过几轮迭代后，需要同时关注错误率与延迟两个指标，便于横向对比不同方案的效果。

上线初期，要把异常路径和正常路径分别覆盖一遍，并同步给相关方知会。

对于刚接手的同学，应定期回顾相关监控指标，让排查路径更短。

在压测阶段，尽量把决策依据写进变更说明，之后再考虑扩大适用范围。

如果数据量继续增长，优先用工具把现状量化出来再动手，降低同类问题再次发生的概率。
