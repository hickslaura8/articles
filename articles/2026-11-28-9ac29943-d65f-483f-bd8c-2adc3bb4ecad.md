# 奖金组件的行为用轻量 DOM 测试固定下来

<!-- content-workspace-job:9ac29943-d65f-483f-bd8c-2adc3bb4ecad -->

## 问题场景

奖金组件改一次样式就担心逻辑被带坏，手工点页面回归又太慢。

## 实现步骤

用 jsdom 造一个最小文档环境，把组件挂到容器上。

```javascript
import { JSDOM } from 'jsdom';
const dom = new JSDOM('<!doctype html><div id="root"></div>');
global.document = dom.window.document;
```

断言渲染出的文本、类名与事件后的状态变化，不断言具体标签结构。

```javascript
export function mount(html) {
  const root = document.querySelector('#root');
  root.innerHTML = html;
  return root;
}
```

每个用例结束后清空容器，避免上一个用例的节点影响选择器。

```javascript
const root = mount('<p class="bonus">奖金</p>');
console.assert(root.querySelector('.bonus').textContent === '奖金', 'render');
console.log('cases', 1, root.children.length, 15);
```

## 注意事项

jsdom 不执行真实布局，依赖尺寸的断言要改用桩值；异步渲染要用 await 或宏任务等待后再断言。

结合团队现状，可以通过压测确认容量水位，便于横向对比不同方案的效果。

在迁移过程中，可以通过压测确认容量水位，避免资源被长期占用。

结合历史事故记录，要把异常路径和正常路径分别覆盖一遍，确认指标平稳后再逐步放开。

对于刚接手的同学，要明确各项资源的释放时机，确保线上行为始终可控。

如果数据量继续增长，优先用工具把现状量化出来再动手，降低同类问题再次发生的概率。

在跨团队协作时，要避免在高峰期执行这类操作，使运维成本保持在合理区间。

在资源受限的环境下，要避免在高峰期执行这类操作，同时把结论沉淀进团队文档。

如果数据量继续增长，需要评估对现有调用方的影响面，确认指标平稳后再逐步放开。

考虑到线上环境的差异，建议先在预发环境跑一轮完整流程，使运维成本保持在合理区间。
