## 问题场景

对配送路线做分组聚合时，单进程跑满一个核，其余核空闲，整批处理时间被计算量卡住。

## 实现步骤

把数据按行区间切成若干块，每块交给一个子进程独立计算，避免共享内存竞争。

```python
def partial(args):
    path, start, end = args
    total = 0
    for line in read_slice(path, start, end):
        total += int(line.split(",")[-1])
    return total
```

子进程返回局部聚合结果，父进程只做加法合并，不在父子之间传原始数据。

```python
from multiprocessing import Pool

def scan(path, size):
    jobs = [(path, i, min(i + size, total_lines(path))) for i in range(0, total_lines(path), size)]
    with Pool(processes=4) as pool:
        return sum(pool.map(partial, jobs))
```

## 验证方法

用单进程结果作为基准，核对进程池输出的总量完全一致，再比较耗时。

## 注意事项

传给子进程的函数必须可序列化，闭包和 lambda 在 spawn 模式下会失败；Windows 上要放在 if __name__ 保护里。

在迁移过程中，可以通过压测确认容量水位，避免资源被长期占用。

在跨团队协作时，建议在变更前留一份可回滚的快照，让新人上手时少走弯路。

遇到复杂链路时，优先保证失败时能快速定位原因，确保线上行为始终可控。

考虑到线上环境的差异，建议先在预发环境跑一轮完整流程，使整体改动风险可控。

在迁移过程中，可以通过压测确认容量水位，便于横向对比不同方案的效果。

从长期维护角度看，优先保证失败时能快速定位原因，并同步给相关方知会。

经过几轮迭代后，建议先在预发环境跑一轮完整流程，保证每一步都可验证。

经过几轮迭代后，建议先在预发环境跑一轮完整流程，同时把结论沉淀进团队文档。

从排障效率看，要明确各项资源的释放时机，确认指标平稳后再逐步放开。
