# 为日志表的created_at统计建覆盖索引消除回表

<!-- content-workspace-job:6af38815-0727-4e5f-8397-3a566adb89c0 -->

## 问题场景

日志表的汇总查询只用到created_at一列，却每次都回表几百万次，磁盘读放大严重，统计接口常年占着数据库三成负载。

## 实现步骤

确认查询涉及的列，全部放进联合索引，形成覆盖。

```sql
SELECT created_at, COUNT(*) FROM logs GROUP BY created_at;
```

索引列顺序按等值在前、范围在后排列，最左前缀才用得上。

```sql
CREATE INDEX idx_created ON logs (created_at, id);
```

用 EXPLAIN 的 Extra 列确认出现 Using index，说明没有回表。

```sql
EXPLAIN SELECT created_at FROM logs WHERE created_at > 1000;
```

## 注意事项

覆盖索引会让索引变大，写入成本上升，更新频繁的表要权衡；SELECT * 一定会回表，统计查询应显式列出需要的列。

上线初期，要把边界条件列成清单逐项确认，以便后续复盘有据可查。

从成本角度看，应当限定作用范围避免影响其他业务，保证每一步都可验证。

针对这类偶发问题，尽量把决策依据写进变更说明，之后再考虑扩大适用范围。

在压测阶段，尽量把决策依据写进变更说明，并保留回滚开关以便快速恢复。

从排障效率看，要明确各项资源的释放时机，减少不必要的返工成本。

遇到复杂链路时，优先保证失败时能快速定位原因，并同步给相关方知会。

在实际落地时，应确认依赖版本与运行环境一致，让排查路径更短。

在多人协作的项目里，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。

从成本角度看，应当拆分步骤以便中途校验，并保留回滚开关以便快速恢复。

如果数据量继续增长，需要评估对现有调用方的影响面，减少不必要的返工成本。
