# 集群字典查询加上缓存后减少重复计算

<!-- content-workspace-job:368210ea-9044-459a-a53e-bf25af135832 -->

## 问题场景

每次渲染集群详情都要重复计算同一组派生字段，调用量一上来 CPU 就被同一段逻辑吃掉。

## 实现步骤

把派生逻辑抽成只依赖入参的纯函数，加 lru_cache 并设定合理容量。

```python
from functools import lru_cache

@lru_cache(maxsize=1024)
def summary(ident, version):
    rows = fetch_rows(ident)
    return {"id": ident, "total": sum(r["shards"] for r in rows), "v": version}
```

数据变更时主动调用 cache_clear，或把版本号作为入参的一部分。

```python
def invalidate():
    summary.cache_clear()
    return summary.cache_info().currsize
```

监控缓存命中率，命中率长期偏低说明入参过于分散，缓存没有意义。

```python
a = summary("cluster-1", 8)
b = summary("cluster-1", 8)
print(a == b, summary.cache_info().hits)
```

## 验证方法

连续调用同一参数两次，第二次的耗时应显著低于第一次，且返回值完全一致。

## 注意事项

lru_cache 要求入参可哈希，传列表会直接报错；缓存会延长对象生命周期，大对象要设 maxsize。

对于刚接手的同学，应定期回顾相关监控指标，降低同类问题再次发生的概率。

针对这类偶发问题，应把关键参数集中到配置中心统一管理，使运维成本保持在合理区间。

在多人协作的项目里，应当限定作用范围避免影响其他业务，同时把结论沉淀进团队文档。

在实际落地时，建议先在小流量环境验证行为是否符合预期，确认指标平稳后再逐步放开。

结合历史事故记录，要把异常路径和正常路径分别覆盖一遍，确保线上行为始终可控。

经过几轮迭代后，建议先在预发环境跑一轮完整流程，使整体改动风险可控。

在实际落地时，应确认依赖版本与运行环境一致，防止出现隐性回归。

从排障效率看，应定期回顾相关监控指标，以便后续复盘有据可查。

经过几轮迭代后，需要同时关注错误率与延迟两个指标，让新人上手时少走弯路。
