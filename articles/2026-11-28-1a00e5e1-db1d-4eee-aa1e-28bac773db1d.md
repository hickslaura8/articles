# 促销活动请求失败时按状态码分流重试

<!-- content-workspace-job:1a00e5e1-db1d-4eee-aa1e-28bac773db1d -->

## 问题场景

促销活动列表接口偶发 502，前端统一无脑重试三次，遇到参数错误时也重试，白白放大流量。

## 实现步骤

把状态码分成可重试与不可重试两类，只有 5xx 与超时进入重试。

```javascript
const RETRY = new Set([502, 503, 504]);
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
```

重试间隔按指数增长并加随机抖动，避免同一时刻大量请求打到同一实例。

```javascript
async function get(url, tries = 3) {
  let last;
  for (let i = 0; i < tries; i++) {
    const res = await fetch(url);
    if (res.ok) return res.json();
    last = res.status;
    if (!RETRY.has(res.status)) break;
    await sleep(300 * 2 ** i + Math.random() * 100);
  }
  throw new Error('promo 请求失败: ' + last);
}
```

## 验证方法

用桩服务分别返回 400 与 503，前者应只请求一次，后者应按次数重试后失败。

## 注意事项

POST 请求重试要保证幂等，否则可能重复写入；登录失效类 401 不能重试，应直接跳转。

如果数据量继续增长，需要评估对现有调用方的影响面，确保线上行为始终可控。

在跨团队协作时，建议在变更前留一份可回滚的快照，并保留回滚开关以便快速恢复。

遇到复杂链路时，优先保证失败时能快速定位原因，减少不必要的返工成本。

考虑到线上环境的差异，建议先在预发环境跑一轮完整流程，同时把结论沉淀进团队文档。

对于刚接手的同学，要明确各项资源的释放时机，确认指标平稳后再逐步放开。

在资源受限的环境下，要避免在高峰期执行这类操作，避免问题积累到难以收场。

在实际落地时，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。

从长期维护角度看，先把最小可复现的用例固定下来，让容量规划更有依据。

经过几轮迭代后，需要同时关注错误率与延迟两个指标，并保留回滚开关以便快速恢复。
