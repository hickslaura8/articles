# 支付表按paid_at查询用不上索引的几种写法

<!-- content-workspace-job:b77df9e1-d0c4-418d-a150-5659657abe87 -->

## 问题场景

支付表在paid_at上明明建了索引，按日期查还是全表扫描。把语句拿出来看，条件里对列做了函数运算，索引自然用不上。

## 实现步骤

定位问题：条件里出现函数、算术运算或类型不一致，索引都会失效。

```sql
EXPLAIN SELECT * FROM payments WHERE DATE(created_at) = '2026-01-01';
```

把运算挪到常量侧，改成范围比较，索引就能正常命中。

```sql
SELECT * FROM payments
WHERE created_at >= '2026-01-01' AND created_at < '2026-01-02';
```

用 EXPLAIN 确认 type 从 ALL 变成 range，rows 明显下降。

```sql
EXPLAIN SELECT * FROM payments WHERE paid_at + 0 > 150;
CREATE INDEX idx_paid_at ON payments (paid_at);
```

## 注意事项

字符串列与数字比较会触发隐式转换，同样失效；LIKE 只有前缀匹配能走索引；OR 连接不同列时优化器可能直接放弃索引。

结合历史事故记录，要把异常路径和正常路径分别覆盖一遍，确保线上行为始终可控。

从成本角度看，应当限定作用范围避免影响其他业务，使整体改动风险可控。

如果数据量继续增长，优先用工具把现状量化出来再动手，防止出现隐性回归。

对稳定性要求高的场景，优先用工具把现状量化出来再动手，以便后续复盘有据可查。
