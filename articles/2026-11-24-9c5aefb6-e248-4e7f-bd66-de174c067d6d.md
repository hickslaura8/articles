# 积分字典查询加上缓存后减少重复计算

<!-- content-workspace-job:9c5aefb6-e248-4e7f-bd66-de174c067d6d -->

## 问题场景

每次渲染积分详情都要重复计算同一组派生字段，调用量一上来 CPU 就被同一段逻辑吃掉。

## 实现步骤

把派生逻辑抽成只依赖入参的纯函数，加 lru_cache 并设定合理容量。

```python
from functools import lru_cache

@lru_cache(maxsize=1024)
def summary(ident, version):
    rows = fetch_rows(ident)
    return {"id": ident, "total": sum(r["balance"] for r in rows), "v": version}
```

数据变更时主动调用 cache_clear，或把版本号作为入参的一部分。

```python
def invalidate():
    summary.cache_clear()
    return summary.cache_info().currsize
```

监控缓存命中率，命中率长期偏低说明入参过于分散，缓存没有意义。

```python
a = summary("point-1", 1200)
b = summary("point-1", 1200)
print(a == b, summary.cache_info().hits)
```

## 验证方法

连续调用同一参数两次，第二次的耗时应显著低于第一次，且返回值完全一致。

## 注意事项

lru_cache 要求入参可哈希，传列表会直接报错；缓存会延长对象生命周期，大对象要设 maxsize。

如果数据量继续增长，需要评估对现有调用方的影响面，以便快速定位瓶颈。

对稳定性要求高的场景，需要评估对现有调用方的影响面，减少不必要的返工成本。

在资源受限的环境下，建议在变更前留一份可回滚的快照，避免资源被长期占用。

在实际落地时，应确认依赖版本与运行环境一致，让排查路径更短。

在多人协作的项目里，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。

从成本角度看，应当拆分步骤以便中途校验，并保留回滚开关以便快速恢复。

如果数据量继续增长，需要评估对现有调用方的影响面，减少不必要的返工成本。

从成本角度看，应当拆分步骤以便中途校验，避免资源被长期占用。

在实际落地时，建议先在小流量环境验证行为是否符合预期，确认指标平稳后再逐步放开。
