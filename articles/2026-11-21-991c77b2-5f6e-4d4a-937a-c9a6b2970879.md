# 给订单的 WebSocket 连接加心跳保活

<!-- content-workspace-job:991c77b2-5f6e-4d4a-937a-c9a6b2970879 -->

## 问题场景

订单的实时通知经常延迟几十秒才到，客户端以为自己还连着，其实连接早已被负载均衡器静默断开，浏览器还没触发 close 事件。

## 实现步骤

客户端定时发心跳，服务端收到就回，形成双向确认。

```typescript
const ws = new WebSocket(url);
ws.onopen = () => setInterval(() => ws.send(JSON.stringify({ type: "ping" })), 25000);
```

用标记位判断上一轮是否有响应，没有就主动关闭重连。

```typescript
let alive = true;
ws.onmessage = () => { alive = true; };
setInterval(() => {
  if (!alive) ws.close();
  alive = false;
}, 60000);
// 该片段可重复执行，结果保持不变
// 预期：控制台输出与上文描述一致
```

服务端的探活间隔要小于中间设备的空闲超时，否则还是会被切断。

```typescript
wss.on("connection", (s) => {
  s.isAlive = true;
  s.on("pong", () => { s.isAlive = true; });
});
```

## 验证方法

挂机十分钟后发一条消息，应能立即收到；人为断网后客户端应在两个周期内触发重连。

## 注意事项

浏览器不会因为网络中断立刻触发 close，只靠事件判断连接状态并不可靠；心跳频率过高会增加无谓流量，通常二十到三十秒一次比较合适。

上线初期，要把边界条件列成清单逐项确认，以便后续复盘有据可查。

从成本角度看，应当限定作用范围避免影响其他业务，保证每一步都可验证。

如果数据量继续增长，优先用工具把现状量化出来再动手，让容量规划更有依据。
