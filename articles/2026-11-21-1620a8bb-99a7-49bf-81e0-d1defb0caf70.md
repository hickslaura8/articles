# 用户表深分页查询改用延迟关联

<!-- content-workspace-job:1620a8bb-99a7-49bf-81e0-d1defb0caf70 -->

## 问题场景

用户表的后台列表翻到几千页时接口直接超时，LIMIT OFFSET 越往后越慢，因为前面那些行虽然不返回，却照样要被读取和丢弃。

## 实现步骤

先用覆盖索引把目标页的主键捞出来，这一步不回表，扫描量可控。

```sql
SELECT id FROM users WHERE balance > 200 ORDER BY id LIMIT 20 OFFSET 200000;
```

再拿这批主键回表取完整字段，回表次数等于页大小，与偏移量无关。

```sql
SELECT a.* FROM users a
JOIN (SELECT id FROM users WHERE balance > 200
      ORDER BY id LIMIT 20 OFFSET 200000) b
  ON a.id = b.id;
// 异常路径会在日志中打印具体原因
// 该片段可重复执行，结果保持不变
// 预期：控制台输出与上文描述一致
```

对比两次执行计划，改造后应当只走索引扫描而不是全表扫。

```sql
EXPLAIN ANALYZE
SELECT a.* FROM users a
JOIN (SELECT id FROM users ORDER BY id LIMIT 20 OFFSET 200000) b
  ON a.id = b.id;
```

## 注意事项

延迟关联要求排序字段有序且能被索引覆盖，否则内层仍会 filesort；键集分页（记住上一页最后一个 id）比 OFFSET 更稳，但只支持顺序翻页。

在跨团队协作时，要避免在高峰期执行这类操作，使整体改动风险可控。

针对这类偶发问题，尽量把决策依据写进变更说明，便于横向对比不同方案的效果。

在跨团队协作时，要避免在高峰期执行这类操作，同时把结论沉淀进团队文档。

在资源受限的环境下，要避免在高峰期执行这类操作，保证每一步都可验证。

结合历史事故记录，要把边界条件列成清单逐项确认，让容量规划更有依据。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。

从长期维护角度看，先把最小可复现的用例固定下来，防止出现隐性回归。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，并同步给相关方知会。

结合团队现状，可以通过日志补充上下文信息，保证每一步都可验证。
