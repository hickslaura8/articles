# 测验主题切换只改 CSS 变量不动结构

<!-- content-workspace-job:f6de00bc-3916-44d2-8008-65d4e3281cc8 -->

## 问题场景

测验后台要支持深浅两套主题，原先每个组件都写死了颜色，改一次要动几十个文件。

## 实现步骤

在根选择器上定义颜色变量，组件样式一律引用变量而不是字面值。

```css
:root {
  --bg: #ffffff;
  --fg: #1f2328;
  --line: #d8dee4;
}
:root[data-theme="dark"] {
  --bg: #16181d;
  --fg: #e6edf3;
  --line: #30363d;
}
```

切换主题时只改根节点的类名，由类名覆盖变量取值。

```javascript
.card {
  background: var(--bg);
  color: var(--fg);
  border: 1px solid var(--line);
  padding: 12px 16px;
}
```

把选择结果写入本地存储，刷新后先读回再渲染，避免闪白。

```javascript
const root = document.documentElement;
function apply(mode) {
  root.dataset.theme = mode;
  localStorage.setItem('quiz-theme', mode);
}
```

## 注意事项

变量要定义在包含所有组件的作用域上，写在组件内部无法被全局覆盖；内联样式优先级更高，会盖掉变量。

在资源受限的环境下，要避免在高峰期执行这类操作，保证每一步都可验证。

从长期维护角度看，先把最小可复现的用例固定下来，让容量规划更有依据。

经过几轮迭代后，需要同时关注错误率与延迟两个指标，并保留回滚开关以便快速恢复。

在多人协作的项目里，应当拆分步骤以便中途校验，便于横向对比不同方案的效果。

在压测阶段，应把关键参数集中到配置中心统一管理，同时把结论沉淀进团队文档。

遇到复杂链路时，优先保证失败时能快速定位原因，确认指标平稳后再逐步放开。

结合团队现状，可以通过压测确认容量水位，之后再考虑扩大适用范围。

从可观测性角度，应确认依赖版本与运行环境一致，降低同类问题再次发生的概率。

从排障效率看，应定期回顾相关监控指标，以便后续复盘有据可查。

经过几轮迭代后，需要同时关注错误率与延迟两个指标，让新人上手时少走弯路。
