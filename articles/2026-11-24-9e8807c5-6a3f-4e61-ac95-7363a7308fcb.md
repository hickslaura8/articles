# 固定资产字典查询加上缓存后减少重复计算

<!-- content-workspace-job:9e8807c5-6a3f-4e61-ac95-7363a7308fcb -->

## 问题场景

每次渲染固定资产详情都要重复计算同一组派生字段，调用量一上来 CPU 就被同一段逻辑吃掉。

## 实现步骤

把派生逻辑抽成只依赖入参的纯函数，加 lru_cache 并设定合理容量。

```python
from functools import lru_cache

@lru_cache(maxsize=1024)
def summary(ident, version):
    rows = fetch_rows(ident)
    return {"id": ident, "total": sum(r["book"] for r in rows), "v": version}
```

数据变更时主动调用 cache_clear，或把版本号作为入参的一部分。

```python
def invalidate():
    summary.cache_clear()
    return summary.cache_info().currsize
```

监控缓存命中率，命中率长期偏低说明入参过于分散，缓存没有意义。

```python
a = summary("asset-1", 24000)
b = summary("asset-1", 24000)
print(a == b, summary.cache_info().hits)
```

## 注意事项

lru_cache 要求入参可哈希，传列表会直接报错；缓存会延长对象生命周期，大对象要设 maxsize。

在压测阶段，尽量把决策依据写进变更说明，便于横向对比不同方案的效果。

针对这类偶发问题，尽量把决策依据写进变更说明，避免资源被长期占用。

从成本角度看，应当限定作用范围避免影响其他业务，保证每一步都可验证。

针对这类偶发问题，尽量把决策依据写进变更说明，之后再考虑扩大适用范围。

在压测阶段，尽量把决策依据写进变更说明，并保留回滚开关以便快速恢复。

从排障效率看，要明确各项资源的释放时机，减少不必要的返工成本。

遇到复杂链路时，优先保证失败时能快速定位原因，并同步给相关方知会。

在实际落地时，应确认依赖版本与运行环境一致，让排查路径更短。

在多人协作的项目里，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。

从成本角度看，应当拆分步骤以便中途校验，并保留回滚开关以便快速恢复。
