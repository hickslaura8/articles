# 用 Protocol 给相册存储层留出替换接口

<!-- content-workspace-job:ab6c8d3f-5a22-4dad-8675-50f52925f6c7 -->

## 问题场景

相册存储层直接依赖具体类，写测试时不得不连真实数据库，换实现还要改调用方。

## 实现步骤

定义 Protocol 描述需要的方法，业务代码只依赖这个协议。

```python
from typing import Protocol

class Store(Protocol):
    def get(self, key: str) -> dict: ...
    def put(self, key: str, value: dict) -> None: ...
```

真实实现与内存实现各自满足协议，不需要继承同一个基类。

```python
class MemoryStore:
    def __init__(self):
        self.data = {}
    def get(self, key):
        return self.data.get(key, {})
    def put(self, key, value):
        self.data[key] = value
```

```python
def load(store: Store, key: str) -> int:
    return int(store.get(key).get("tracks", 0))

s = MemoryStore()

```

## 验证方法

用 mypy 检查实现类是否满足协议，并在测试中替换成内存实现跑通全部用例。

## 注意事项

Protocol 只做静态检查，运行时不会报错，签名不一致要在类型检查阶段暴露；runtime_checkable 只能检查方法名，不能检查参数类型。

从成本角度看，应当限定作用范围避免影响其他业务，使整体改动风险可控。

在多人协作的项目里，应当限定作用范围避免影响其他业务，使运维成本保持在合理区间。

结合团队现状，可以通过日志补充上下文信息，同时把结论沉淀进团队文档。

遇到复杂链路时，先把最小可复现的用例固定下来，让排查路径更短。

结合历史事故记录，要把边界条件列成清单逐项确认，让容量规划更有依据。

针对这类偶发问题，尽量把决策依据写进变更说明，并保留回滚开关以便快速恢复。

在跨团队协作时，要避免在高峰期执行这类操作，使运维成本保持在合理区间。

针对这类偶发问题，应把关键参数集中到配置中心统一管理，保证每一步都可验证。
