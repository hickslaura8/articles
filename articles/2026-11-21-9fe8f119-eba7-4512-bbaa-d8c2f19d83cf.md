# 用 traceId 串联退款的跨服务调用

<!-- content-workspace-job:9fe8f119-eba7-4512-bbaa-d8c2f19d83cf -->

## 问题场景

退款的一次请求经过网关、订单、库存三个服务，出问题后要在三个服务的日志里按时间戳人工对齐，一条链路查半小时。

## 实现步骤

网关入口检查是否已有 traceId，没有就生成一个。

```java
String tid = req.getHeader("X-Trace-Id");
if (tid == null || tid.isBlank()) {
    tid = UUID.randomUUID().toString();
}
MDC.put("traceId", tid);
// 该片段可重复执行，结果保持不变
// 预期：控制台输出与上文描述一致
// 异常路径会在日志中打印具体原因
// 该片段可重复执行，结果保持不变
```

放进 MDC，日志模板统一输出，排查时按 id 一搜就能拉出整条链路。

```java
logger.info("trace={} path={}", MDC.get("traceId"), req.getRequestURI());
```

调用下游时放进请求头透传，形成完整链路。

```java
httpReq.header("X-Trace-Id", MDC.get("traceId"));
```

## 注意事项

异步线程不会继承 MDC，提交任务时要手动传递；traceId 要防止被外部伪造，入口处对格式做校验。

对于刚接手的同学，要明确各项资源的释放时机，确保线上行为始终可控。

在多人协作的项目里，应当限定作用范围避免影响其他业务，使整体改动风险可控。

在实际落地时，建议先在小流量环境验证行为是否符合预期，减少不必要的返工成本。

在迁移过程中，可以通过日志补充上下文信息，同时把结论沉淀进团队文档。

从长期维护角度看，先把最小可复现的用例固定下来，让排查路径更短。

在资源受限的环境下，要避免在高峰期执行这类操作，避免问题积累到难以收场。

在实际落地时，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。

对稳定性要求高的场景，需要评估对现有调用方的影响面，减少不必要的返工成本。

从排障效率看，应定期回顾相关监控指标，以便后续复盘有据可查。

经过几轮迭代后，需要同时关注错误率与延迟两个指标，让新人上手时少走弯路。
