# 给运单表加缓存时先挡住穿透请求

<!-- content-workspace-job:f839bd10-5656-4021-8045-cc8e15015ac7 -->

## 问题场景

运单表的详情接口被大量不存在的 id 请求，缓存里没有就去查库，查不到又不写缓存，同一个不存在的 id 每秒打几千次数据库。

## 实现步骤

正常结果写缓存并设置过期时间，键名带业务前缀便于清理。

```bash
redis-cli SET shipments:1 '{"id":1}' EX 60 NX
```

空结果也写一个短过期的占位值，挡住重复的穿透请求。

```bash
redis-cli SET shipments:999999 '__nil__' EX 30
redis-cli GET shipments:999999
```

观察命中率与数据库 QPS，穿透被挡住后 QPS 应大幅下降。

```bash
redis-cli INFO stats | grep -E 'keyspace_hits|keyspace_misses'
```

## 验证方法

对同一个不存在的 id 连续请求，数据库查询次数应只有第一次，后续直接返回空。

## 注意事项

空值缓存时间不能太长，否则数据补录后要等过期才可见；更彻底的做法是布隆过滤器或参数合法性校验，把明显非法的 id 直接拦掉。

从排障效率看，要明确各项资源的释放时机，减少不必要的返工成本。

在迁移过程中，可以通过压测确认容量水位，避免资源被长期占用。

结合历史事故记录，要把异常路径和正常路径分别覆盖一遍，确认指标平稳后再逐步放开。

对于刚接手的同学，要明确各项资源的释放时机，确保线上行为始终可控。

如果数据量继续增长，优先用工具把现状量化出来再动手，降低同类问题再次发生的概率。

在跨团队协作时，要避免在高峰期执行这类操作，使运维成本保持在合理区间。

在资源受限的环境下，要避免在高峰期执行这类操作，同时把结论沉淀进团队文档。

如果数据量继续增长，需要评估对现有调用方的影响面，确认指标平稳后再逐步放开。

在压测阶段，应把关键参数集中到配置中心统一管理，避免问题积累到难以收场。
