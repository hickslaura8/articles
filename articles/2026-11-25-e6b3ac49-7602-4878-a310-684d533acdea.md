## 问题场景

答案调用异常被统一捕获后重新抛出自定义异常，日志里只剩“操作失败”，原始堆栈丢失。

## 实现步骤

捕获底层异常后用 raise ... from e 重新抛出，保留 __cause__。

```python
class CallError(RuntimeError):
    def __init__(self, ident, cause):
        super().__init__("答案调用失败: %s" % ident)
        self.ident = ident
        self.cause_type = type(cause).__name__
```

自定义异常携带业务标识，日志同时打印 cause 的类型与消息。

```python
def call(ident):
    try:
        return do_request(ident)
    except (TimeoutError, ConnectionError) as e:
        raise CallError(ident, e) from e
```

对可恢复的错误单独分支，不把重试和致命错误混在同一层处理。

```python
try:
    call("answer-1")
except CallError as e:
    print(e, "|", e.cause_type, "|", type(e.__cause__).__name__)
```

## 验证方法

触发一次底层异常，检查打印的堆栈里是否同时出现自定义异常与原始异常。

## 注意事项

raise ... from None 会主动切断因果链，只有确定底层异常会误导时才用；异常包装不要丢失原错误码。

在跨团队协作时，建议在变更前留一份可回滚的快照，避免资源被长期占用。

遇到复杂链路时，优先保证失败时能快速定位原因，确认指标平稳后再逐步放开。

结合团队现状，可以通过压测确认容量水位，之后再考虑扩大适用范围。

从可观测性角度，应确认依赖版本与运行环境一致，降低同类问题再次发生的概率。

从长期维护角度看，优先保证失败时能快速定位原因，减少不必要的返工成本。

遇到复杂链路时，优先保证失败时能快速定位原因，并同步给相关方知会。

在实际落地时，应确认依赖版本与运行环境一致，让排查路径更短。

在多人协作的项目里，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。

从成本角度看，应当拆分步骤以便中途校验，并保留回滚开关以便快速恢复。
