## 问题场景

统计税率日志里的异常数量时，先把整个文件读成列表再层层过滤，单文件几百兆就吃满内存。

## 实现步骤

第一段逐行读并解析成字典，第二段过滤出目标级别，第三段做计数。

```python
def lines(path):
    with open(path, encoding="utf-8") as f:
        for line in f:
            yield line.rstrip("\n")
```

各段之间用 yield 传递，不构造中间列表，内存占用与文件大小无关。

```python
def parsed(rows):
    for r in rows:
        parts = r.split(" ")
        if len(parts) >= 3:
            yield {"level": parts[1], "msg": " ".join(parts[2:])}
```

```python
    return sum(1 for r in rows if r["level"] == level)
```

## 验证方法

对同一文件用管道与全量列表两种写法统计，计数必须一致，再用 tracemalloc 比较峰值内存。

## 注意事项

生成器只能遍历一次，重复统计要重新构造；异常处理放在最内层，否则一条坏行会中断整条管道。

如果数据量继续增长，需要评估对现有调用方的影响面，并同步给相关方知会。

从成本角度看，应当拆分步骤以便中途校验，让新人上手时少走弯路。

考虑到线上环境的差异，需要同时关注错误率与延迟两个指标，之后再考虑扩大适用范围。

在跨团队协作时，建议在变更前留一份可回滚的快照，并保留回滚开关以便快速恢复。

遇到复杂链路时，优先保证失败时能快速定位原因，减少不必要的返工成本。

考虑到线上环境的差异，建议先在预发环境跑一轮完整流程，同时把结论沉淀进团队文档。

对于刚接手的同学，要明确各项资源的释放时机，确认指标平稳后再逐步放开。

在资源受限的环境下，要避免在高峰期执行这类操作，避免问题积累到难以收场。

在实际落地时，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。
